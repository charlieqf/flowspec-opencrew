这次扫描还补充了之前没有完全沉淀的经验：

- 测试前必须先定义“不合规案例”，否则结果会污染模型排序。
- 所有测试必须保存 `prompt.txt` 和脱敏后的 `request_params.json`，否则无法解释为什么某个结果好或坏。
- HTML 标注工具不是附属物，而是实验闭环的核心部分。
- 人工标注必须结构化，不应只留下自由文本。
- `localStorage` 只适合临时保存，最终分析必须导出 JSON。
- 大模型无法直接读取浏览器 localStorage，必须通过导出的 review JSON 进入复盘流程。
- 单轮实验不追求一次得出答案，而是要产生下一轮更小、更准的实验计划。
- 视频模型原生音频不稳定时，应把画面生成和 TTS 语音生成拆开评估。

## 二、总原则

### 2.1 所有实验必须可复现

每个 case 必须能回答四个问题：

1. 用了哪个模型？
2. 传了哪些输入文件？
3. 提示词是什么？
4. 实际调用参数是什么？

如果这四项缺一项，就不能进入正式评估排名。

### 2.2 先定义边界，再运行模型

不要先跑再想怎么评估。  
每轮测试开始前必须先写清楚：

- 本轮目标是什么
- 哪些 case 合格
- 哪些 case 不合格
- 哪些指标是硬淘汰
- 哪些指标只是扣分
- 是否允许模型生成声音
- 是否采用外部 TTS
- 是否必须带图片输入
- 参考图、SRT、WAV 的路径和时长

### 2.3 实验要从广到窄

推荐节奏：

1. Smoke test：确认 API、鉴权、下载、保存链路能跑通。
2. 能力覆盖测试：广泛测试模型输入能力，例如单图、首尾帧、多图、音频。
3. 非合规剔除：移除纯文字、无参考图、错误画幅、错误输入模式。
4. 核心候选测试：用更严格提示词重跑少量模型。
5. 生产接近测试：统一 8 秒或目标生产时长测试。
6. 链式测试：用上一段尾帧做下一段首帧，验证长视频拼接策略。
7. 总结入库：把结论写入模型指南、提示词指南和工作方式指南。

### 2.4 每一轮都要产出下一轮假设

一轮实验结束，不只是给排名，还要回答：

- 哪些问题已经解决？
- 哪些问题变少但未根治？
- 哪些模型应淘汰？
- 哪些模型值得重跑？
- 哪些失败可能是提示词问题？
- 哪些失败是能力/API/服务端问题？
- 下一轮应该减少哪些 case？
- 下一轮应该新增哪些硬约束？

## 三、标准实验生命周期

### 3.1 阶段 0：任务定义

必须先写一段任务定义：

```text
本轮实验目标：
- 测试对象：
- 参考资产：
- 目标时长：
- 输出画幅：
- 是否要求音频：
- 是否使用外部 TTS：
- 本轮不测试的内容：
- 硬淘汰条件：
```

示例：

```text
目标：验证固定机位口播视频中，模型能否在 8 秒内保持人物、产品、背景和机位一致。
不测试：纯文字生成，不测试无图输入，不测试背景重绘。
硬淘汰：非 9:16、无参考图、产品打开、人物明显换脸、字幕残留、镜头明显推拉。
```

### 3.2 阶段 1：资产准备

每轮至少准备：

| 资产 | 要求 |
| --- | --- |
| 首帧图 | 真实目标画面，不是模型重新生成图 |
| 中间参考图 | 用于多图参考时保持姿势、产品和背景一致 |
| 尾帧图 | 用于首尾帧或链式生成收束 |
| SRT | 与目标时长一致，文本已替换为当前产品 |
| WAV | 如果测试音频输入，必须按 SRT 时长裁剪 |
| 约束文档 | 写清楚画幅、机位、产品、字幕、声音等硬限制 |

资产准备经验：

- 单图测试只传首帧图。
- 首尾帧测试传首帧和尾帧。
- 多图参考测试传固定顺序的参考图，不要混入临时生成图。
- 音频输入测试必须同时传图像，不能做纯音频或文字+音频。
- WAV 必须按 SRT 时间裁剪，不能传整段大音频。
- SRT 不能只改产品名，还要检查动作词是否会误导视频模型做动作。

### 3.3 阶段 2：能力清单和案例设计

先按模型能力分组，再设计 case。

标准类别：

| 类别 | 目的 | 输入 |
| --- | --- | --- |
| `duration_min` | 验证模型最短可用时长 | 最小 SRT + 至少一张图 |
| `single_image` | 验证单首帧图生视频 | `first_image` |
| `first_last` | 验证首帧和尾帧控制 | `first_image` + `last_image` |
| `image_reference` | 验证多图参考一致性 | 多张 reference images |
| `audio_input` | 验证图片 + 音频输入 | 图片 + 裁剪 WAV |
| `chain_segments` | 验证长视频分段拼接 | 上一段尾帧作为下一段首帧 |
| `risk_recheck` | 复验高风险模型能否被提示词修复 | 严格约束 + 明确风险说明 |
| `comparison_sample` | 保存特殊对照样本 | 例如 12 秒 lastFrame 对照 |

案例设计规则：

- case id 必须包含类别、provider、model、时长或模式。
- 每个 case 都要有明确测试目的。
- 每个 case 都要写预期检查项。
- 同一轮测试里，除非测试变量本身不同，否则其他条件要尽量一致。
- 不要把已知不合规 case 混入正式排名。

推荐 case 字段：

```json
{
  "case_id": "single_image__provider__model__8s",
  "provider": "provider_name",
  "model": "model_name",
  "category": "single_image",
  "duration_seconds": 8,
  "srt_file": "validation_plan/srt_min_08s.srt",
  "prompt_file": "base_prompt.txt",
  "objective": "验证单图输入下是否保持人物、产品、背景、机位一致",
  "inputs": {
    "mode": "first_frame",
    "first_image": "1.png",
    "images": ["1.png"],
    "audio": ""
  },
  "expected_checks": [
    "9:16",
    "固定机位",
    "人物一致",
    "产品完整",
    "无字幕"
  ]
}
```

### 3.4 阶段 3：提示词标准

提示词必须分层：

1. 通用硬约束
2. 输入资产说明
3. 视觉约束
4. 动作约束
5. 产品约束
6. 字幕/文字约束
7. 声音/SRT 约束
8. 模型专项补强
9. 验收标准

通用硬约束示例：

```text
Use only the provided image inputs. Do not generate from text alone.
The camera is locked in one fixed position.
Output must be vertical 9:16.
No pan, tilt, dolly, zoom, reframing, camera shake, or angle switch.
The product must remain closed, intact, visible, and unchanged.
Do not open, unwrap, tear, pour, eat, drink, or demonstrate the product.
No subtitles, captions, title text, watermark, UI, or generated on-screen text.
If audio is generated, it must be speech only. No background music, soundtrack, ambient music, or sound effects.
```

经验：

- 如果模型会把 SRT 里的文字变成动作，要写明“把 SRT 只当口播台词，不当动作指令”。
- 如果模型会放下产品，要写明产品必须始终在手中、胸口以上、正面可见。
- 如果模型会重新生成产品，要写明输入图中的产品是同一件实物，不是风格参考。
- 如果模型会换镜头，要写明“one continuous locked-camera take”。
- 如果模型会输出字幕，要同时在 prompt 和验收标准里禁止。
- 如果模型语音不可靠，要把提示词改成“画面优先、自然口型、最终可外部 TTS”。

### 3.5 阶段 4：运行和调用记录

运行脚本必须为每个 case 保存：

| 文件 | 内容 |
| --- | --- |
| `prompt.txt` | 实际发送给模型的完整提示词 |
| `request_params.json` | 脱敏后的 endpoint、payload、duration、视觉输入、音频输入、prompt hash |
| `output.mp4` | 下载后的视频结果 |
| `results.json` | 全部 case 的结构化结果 |
| `results.md` | 方便人读的结果表 |

`request_params.json` 必须脱敏：

- API key 不落盘。
- 图片/音频二进制不落盘。
- 保留本地文件路径，标明传输方式。
- 保留 `prompt_sha256`，方便判断 prompt 是否变化。
- 保留 endpoint 和 payload 结构，方便排查能力或参数错误。

运行结果必须记录：

- `status`
- `elapsed_seconds`
- `output_duration_seconds`
- `error`
- `prompt_path`
- `request_params_path`
- `output`

失败不要只写“failed”，必须保存 provider response 或关键错误摘要，例如：

- `INVALID_ARGUMENT`
- `moderation_blocked`
- `Input should be first_frame`
- `server internal error`
- `no video URL`
- 下载失败
- 时长不对
- 文件无效

### 3.6 阶段 5：HTML 标注工具

每轮正式测试完成后，都要生成一个 HTML 标注页。

标准列：

| 列 | 说明 |
| --- | --- |
| RUN | 哪一轮运行目录 |
| 案例名称 | case id 和 category |
| 测试目的 | 中文说明该 case 测什么 |
| 模型 | provider + model |
| 调用参数 | 可展开 `request_params.json`，并链接 `prompt.txt` |
| 时长 | 实际时长 + 目标时长 |
| 视频播放链接 | 内嵌 video + 打开链接 |
| 效果评价 | 结构化人工标注 |

页面必须提供：

- 总数、完成数、失败数、成功率统计。
- status filter。
- category filter。
- 搜索。
- `prompt.txt` 链接。
- `request_params.json` 链接。
- 视频内嵌播放。
- 标注内容自动保存到 localStorage。
- `Export Reviews JSON`。
- Copy / Paste 单条评论，方便用大模型辅助整理评论。

标准标注字段：

| 字段 | 中文问题 |
| --- | --- |
| `product_text_clear` | 产品文字是否清晰 |
| `speech_text_accurate` | 语音文字是否准确 |
| `lip_sync_accurate` | 口型是否准确 |
| `person_accurate` | 人物是否准确 |
| `unreasonable_content` | 画面内是否有不合理的内容 |
| `other_issues` | 其它问题 |
| `production_decision` | 是否可进入生产，建议新增 |

`production_decision` 建议取值：

- `yes`
- `maybe`
- `no`
- `rerun_with_prompt_fix`
- `provider_capability_issue`
- `discard`

### 3.7 阶段 6：人工标注和导出

标注时不要只写“好/不好”，要写成可归类的问题。

推荐写法：

```text
产品文字是否清晰：大字清晰，小字不清晰。
语音文字是否准确：有吞音，产品名不完整。
口型是否准确：可接受，但部分句子对不上。
人物是否准确：人物准确，衣服和麦克风一致。
画面内是否有不合理的内容：结尾把产品放下，并拿出不同包装。
其它问题：值得重跑，可能是 SRT 诱导了动作。
是否可进入生产：rerun_with_prompt_fix
```

标注保存规则：

- localStorage 只作为浏览器临时保存。
- 关闭网页再打开，同一浏览器、同一路径下通常还在。
- 大模型不能直接访问 localStorage。
- 必须导出 JSON 后，才能进入自动汇总和复盘。
- 导出的 review JSON 是人工评价的事实源。

### 3.8 阶段 7：结果汇总

每轮实验结束后，必须生成汇总报告。

报告至少包含：

1. 运行目录。
2. 计划总数。
3. 完成数。
4. 失败数。
5. 失败原因表。
6. 异常类型统计。
7. 按模型排序。
8. 按类别排序。
9. 值得重跑的 case。
10. 不建议继续测试的 case。
11. 本轮解决的问题。
12. 本轮新增的问题。
13. 下一轮计划。

异常标签建议统一：

| 标签 | 说明 |
| --- | --- |
| `画幅错误` | 输出不是目标比例，例如 16:9 而不是 9:16 |
| `无图不合规` | 没有传参考图 |
| `人物不一致` | 人脸、年龄、服装、发型漂移 |
| `产品不一致` | 产品换包装、换颜色、换形态 |
| `产品文字不清` | 关键产品文字不可辨认 |
| `产品被打开` | 开盒、撕袋、拿出内包装 |
| `额外产品` | 生成额外盒子、袋子或无关产品 |
| `镜头不固定` | 推拉、晃动、切镜头、重新构图 |
| `字幕残留` | 出现字幕、水印、UI、屏幕文字 |
| `SRT不准` | 语音漏字、吞音、改语言、改产品名 |
| `口型不准` | 嘴型和语音或口播节奏明显不匹配 |
| `尾帧不生效` | 首尾帧路径未自然过渡到尾帧 |
| `段间不连续` | 链式拼接时身份、背景、声音或曝光变化 |
| `逐段变暗` | 链式生成亮度或色温不断漂移 |
| `服务端失败` | API 或 provider 内部错误 |
| `审核失败` | moderation blocked |

### 3.9 阶段 8：排行榜和决策

不要只给一个总排名。至少要给三个排名：

1. 画面控制排名  
   看人物、产品、背景、机位、画幅、字幕。

2. SRT/声音排名  
   看语音文字、产品名、口型、音画同步。

3. 综合排名  
   按实际生产策略加权。

如果生产策略采用外部 TTS，综合排名应提高画面权重，降低模型原生语音权重。

推荐权重：

| 策略 | 画面 | 产品文字 | 人物 | 机位 | 语音/SRT | 口型 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 视频模型自带声音 | 25% | 20% | 15% | 15% | 15% | 10% |
| 外部 TTS 策略 | 35% | 25% | 20% | 15% | 0% | 5% |
| 只测画面复刻 | 40% | 30% | 20% | 10% | 0% | 0% |

### 3.10 阶段 9：下一轮提升

每轮复盘必须转化为下一轮实验计划。

转换方式：

| 发现 | 下一轮动作 |
| --- | --- |
| 无图导致结果无关 | 所有 case 强制带图，历史无图剔除 |
| 产品被打开 | prompt 加“全程闭合、在手中、不可拆、不可演示” |
| 画幅错误 | 参数和 prompt 同时写 9:16 / 720x1280 |
| 语音吞音 | 走外部 TTS，视频只保画面和口型节奏 |
| 模型服务端失败 | 低优先级重跑，不进入质量排名 |
| 模型审核失败 | 简化 prompt 或暂时淘汰 |
| 尾帧不生效 | 单独测试首尾帧，不假设生产可用 |
| 链式逐段变暗 | 加曝光锁定，必要时后处理统一色彩 |
| 段间人物变 | 加 first-frame lock 和尾帧继承约束 |
| SRT 诱导动作 | 明确 SRT 只作为台词，不作为动作指令 |

## 四、硬淘汰规则

以下结果不进入模型质量排名，只能作为失败样本或风险样本：

- 没有图片输入。
- 输出不是目标画幅。
- 人物和参考图完全无关。
- 产品和参考图完全无关。
- 产品打开、拆包、撕袋、倒出、吃喝，除非任务明确要求。
- 出现字幕、水印、UI、额外屏幕文字。
- 镜头明显推拉、晃动、切镜头，且任务要求固定机位。
- 模型重新生成一张静态图再做视频，而不是使用输入参考图。
- 音频测试没有同时传图像。
- WAV 没有按 SRT 时长裁剪。
- prompt 或 request params 没有保存。

## 五、测试轮次设计经验

### 5.1 第一轮：能力发现

目标：

- 找出模型最短时长。
- 找出支持单图、首尾帧、多图、音频的模型。
- 找出 API 参数是否能跑通。

容易踩坑：

- prompt-only 结果污染排序。
- 模型生成和参考图无关。
- 纯文字模型看起来能跑，但不适合参考图一致性任务。
- SRT 和音频未按时长裁剪。

沉淀：

- 所有 case 必须带图。
- 纯文字/无图 case 进非合规清单。
- 每个模型能力要写进能力文档。

### 5.2 第二轮：统一 8 秒生产接近测试

目标：

- 不再只测最短时长。
- 用统一 8 秒 SRT、统一参考图、统一产品约束测试质量。

有效改进：

- 测试规模从大撒网收敛到核心 15 个。
- 所有 case 都带图片输入。
- 产品、SRT、画幅和机位约束统一。
- 产品拆包、画幅错误、人物漂移显著减少。

仍然保留的问题：

- 部分模型会放下产品。
- 部分模型吞音。
- 多图可能拉长身体。
- R2V 仍可能输出 16:9。
- 图片 + 音频可能诱导产品动作。

### 5.3 第三轮：链式最短片段

目标：

- 用最短片段拼接成约 8-12 秒。
- 上一段尾帧作为下一段首帧。
- 验证能否扩展到 1 分 30 秒生产。

关键经验：

- 链式方向可行，但模型差异很大。
- Veo 真实感强，但会放下产品或换产品。
- Wan 产品文字和语音强，但可能逐段变暗。
- Grok 产品稳定、异常少，但 2 秒语音容易不完整。
- Sora Pro 优于 Sora，但尾帧继承仍需补强。
- HappyHorse 拼接后音画可能不同步，最终音轨建议外部 TTS。
- 12 秒 lastFrame 结果应保留为对照，不要强行丢弃。

## 六、长视频复刻推荐策略

如果目标是复刻约 1 分 30 秒固定机位口播：

1. 不要让视频模型一次性生成 90 秒。
2. 按 2-4 秒或模型稳定时长切片。
3. 每段都必须带图像参考。
4. 第一段用真实首帧。
5. 后续段用上一段尾帧作为首帧。
6. 最后一段尽量用目标尾帧或目标状态收束。
7. 每段只要求自然口型和轻微动作。
8. 完整声音用外部 TTS 生成。
9. 拼接后统一替换音轨。
10. 每 5-10 段做一次人工抽检。

生产优先级：

| 目标 | 推荐策略 |
| --- | --- |
| 画面准确 | 视频模型只生成画面，外部 TTS 后配 |
| 声音准确 | 用 TTS 保证产品名和 SRT，不依赖视频模型原生音频 |
| 产品准确 | 首先用 GPT 图像模型准备稳定首帧/关键帧 |
| 段间自然 | 尾帧继承 + 曝光锁定 + 统一后处理 |
| 成本可控 | 先小样本 smoke，再跑核心候选，不跑全量无关模型 |

## 九、标准 HTML 标注工具要求

一个合格的标注 HTML 必须满足：

- 不依赖远程服务，`file://` 可打开。
- 视频路径使用相对路径或绝对 `file://` 兼容路径，确保浏览器能播放。
- 支持按 status 和 category 筛选。
- 支持搜索 run、case、model、purpose。
- 展示总数、完成数、失败数、成功率。
- 展示中文测试目的。
- 展示 prompt 和 request params 链接。
- 标注字段分开填写。
- 支持 Copy / Paste 单条评价。
- 自动保存到 localStorage。
- 支持导出 JSON。

如果 HTML 看不到视频，优先检查：

1. `video src` 是否是相对当前 HTML 的有效路径。
2. 输出 MP4 是否存在。
3. 浏览器是否支持该编码。
4. 过滤器是否把行过滤掉。
5. 数据源是否为空。
6. HTML 生成时 output base 是否正确。

## 十一、把经验写回指南的标准

不是所有现象都要立刻写进通用指南。建议按以下规则入库：

| 现象 | 处理 |
| --- | --- |
| 只出现一次，可能是偶发 | 写入本轮报告，不写入通用指南 |
| 同一模型重复出现 | 写入模型专项指南 |
| 跨模型重复出现 | 写入通用工作方式指南 |
| 和产品/人物类型强相关 | 写入任务提示词指南 |
| 和 API 参数相关 | 写入模型能力文档或 runbook |
| 和标注/评估相关 | 写入工作方式指南 |
| 和生产选择相关 | 写入模型优先级指南 |

本次已确认应写入通用指南的经验：

- 无图 case 不合规。
- prompt 和 params 必须保存。
- 标注必须结构化。
- localStorage 只是临时存储，最终要导出 JSON。
- 音频要按 SRT 裁剪。
- 视频模型原生语音不可靠时，采用外部 TTS。
- SRT 文字不能诱导模型做动作。
- 每轮结束必须产生下一轮计划。

## 十二、下一步建议

为了让这套流程更稳，后续可以继续补三件事：

1. 在 HTML 标注工具里增加 `production_decision` 字段。
2. 在汇总脚本里自动根据人工标注生成异常标签。
3. 在每次生成视频前自动校验 case 是否带图、SRT/WAV 是否匹配、prompt/params 是否会保存。

最终目标不是找到一个“永远最好”的模型，而是建立一套能持续发现、验证、淘汰、优化模型路线的方法。这样换产品、换人物、换时长、换模型时，实验不会重来一遍，而是沿着已有经验继续长出来。
