Why FlowSpec here

受监管决策不是一条自动化直线

这个场景同时包含可并行但可信度不同的外部证据、可解释的政策决策、临界案件的人工作业，以及不可盲目重放的签约与放款副作用。模型可以抽取事实，但不能成为授信政策或放款事实的权威。

01

多源证据并行且可能冲突

规范支持

征信、欺诈和收入核验作为独立 Step 并行执行，以 typed Artifact 汇合到风险决策；每份正式证据都关联生产 Attempt 的输入摘要，并有 Runtime 内容 hash 与业务 binding。

规范约束

AI Profile 限定模型、数据传输和输出 Schema；模型只发布候选事实，政策 Step 必须消费可验证 Artifact，不能让摘要覆盖来源数字。

02

直通审批与人工责任并存

规范支持

最小 when guard 选择直通或 Human Task；确认步骤物化 work item，并把 actor、role、reason、decision、input hash 和 revision 写进 Run。

规范约束

人工决定必须匹配 allowed_decisions、授权角色和 expected revision；未激活分支递归关闭为 skipped，不能留下永远等待的伪 pending。

03

拒绝、退回修改和放款都是正常业务结果

规范支持

exactly_one_outcome 明确拒绝通知、补件请求与放款回执三种完成契约；补正资料后创建 superseding Run，而不在原 DAG 中画返工回边。

规范约束

放款标为 reconcilable 并使用稳定 operation key；响应不明时先对账，不能自动重发。每个 outcome 都必须有终点 Step 和可审计回执。

FlowSpec 在本场景中的作用

FlowSpec 把“模型意见、政策结论、人工责任、客户接受和资金副作用”分成不同权威层，使一次审批既能自动化，又能解释为什么放行、为什么拒绝，以及修订后为什么必须产生新 Run。

决策层建议 先看本导读、流程图和 outcome，理解业务控制与可追责结果。开发团队建议 再下钻运行记录、Artifact、AI/成本治理和规范透视，核对实现契约。
Executive glossary

结合本场景看懂关键术语

DAG（有向无环流程图）
这次审批只从材料向决定、签约和放款前进；需要补正征信时另开新 Run，不在原流程里倒着跳。
Run（一次有边界执行）
同一笔贷款申请的一次审批版本。第二个 Run 代表资料修订后的重审，业务身份不变、输入哈希改变。
Artifact（可追踪业务产物）
征信报告、风险结论或放款回执不只是文件：记录来源步骤、内容校验和与申请 binding，并通过 producer Attempt 关联输入版本。
Human Task（人工责任节点）
系统真正创建给风控人员的待办；决定必须留下谁、以什么角色、基于哪版输入、为什么批准。
Reconcilable（先对账再补做）
放款响应丢失时，先用业务操作键向账本查询是否已发生；不能因超时直接再放一次款。

Typed evidence plane

Author burden · minimal

Tool 只交 payload

流程作者声明 output Schema；只有存在业务对齐需求才写 binding_keys。Tool 不计算 hash、不生成 Artifact ID，也不复制 Run 元数据。

Runtime · automatic

finalize 一次计算

Runtime 生成版本 artifact_id、流式计算内容 sha256/size；声明输入与冻结 Tool/Profile 的摘要只存 producer Attempt 一次。

Out of scope · lightweight

临时文件明确排除

Working / logs / Prompt / .staging / SessionOutput projection 不承担业务 binding 或派生摘要，也不能被当作可复用正式产物。

为什么不在 Artifact 重复输入 hash？一个 Attempt 可能发布多个 Artifact。每条记录只保留 producer attempt_id，页面从 Attempt/Fanout Item 解析唯一的 input_snapshot_hash；便携导出需要时才内联。
为什么四个 Demo 的 binding 都非空？贷款、监管报告、尽调和视频产物都需要跨 Run 按 application / entity / matter / project 对齐；这是场景需要，不是全局强制。无 join、re-bind 或跨 Run 对齐的一次性正式产物可省略 binding_keys。

输入到输出的约束链

  1. session 输入原始文件不可原地覆盖；修订产生新 path/hash。
  2. Run 输入0_SessionContext/InputManifest.json 冻结本次声明输入。
  3. Step 输入Manifest/locator 解析；Adapter staging 只是 Attempt 临时副本。
  4. 中间过程Working 可清，不承担业务 binding/派生摘要，不能被下游当正式产物。
  5. 正式输出先写 .staging；finalize 自动生成版本 ID/hash，再原子发布到既有 Output。
  6. 对外目录SessionOutput 只做可重建投影；canonical Manifest 保持唯一。
为什么 task 没有目录？

OpenCrew 的 session 与 task 1:1 配对。task 从数据库引用 session、Run 与 Artifact ID；再复制一棵 task 文件树只会制造双份字节和清理竞态。
