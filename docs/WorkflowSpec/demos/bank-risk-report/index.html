Why FlowSpec here

报告可信度来自数据切片与控制链，而非文案

银行风险报告必须证明交易、支付和总账来自同一冻结 data cut，质量例外经过授权，指标由确定性计算产生，LLM 叙述只引用这些权威数字，最后还要签署并留下可对账的分发事实。

01

多源冻结后才能三路汇合

规范支持

三个根 Step 独立冻结交易、支付和总账，Reconciliation 与 DQReport 通过显式 AND-join 汇合；Artifact binding 固定 entity、period 和 data_cut_id。

规范约束

后续不得混用不同 data cut，也不能凭文件存在判定就绪；producer 输入摘要、内容 hash、Schema 或声明的 binding 任一不符都不能进入指标计算。

02

DQ waiver 是例外，不是伪装通过

规范支持

质量异常创建独立 Human Task，批准或拒绝结果写成 DQWaiverDecision；拒绝会完整结束为 remediation outcome，重述数据创建新 Run。

规范约束

waiver 必须绑定输入快照、角色、理由和 revision；它不能改写原 DQReport，也不能把未经解释的差异标成普通 pass。

03

指标、叙述、签署和分发四权分离

规范支持

确定性 Step 计算 RiskMetrics，受 grounding/evidence 约束的模型生成 narrative，再与合规附件组装；签署可批准分发，也可用独立修订请求正常收口。

规范约束

LLM 不能重算或覆盖监管数字；Profile 禁止静默 fallback，Usage 单独计费；分发是 reconcilable operation，必须保留 operation key 与 receipt。

FlowSpec 在本场景中的作用

FlowSpec 让报告的每句话都能回到冻结数据、对账控制、指标版本和审批责任；即使数据质量不足，流程也以“请求修复”正常结束，而不是用一个 completed 状态掩盖控制失败。

决策层建议 先看本导读、流程图和 outcome，理解业务控制与可追责结果。开发团队建议 再下钻运行记录、Artifact、AI/成本治理和规范透视，核对实现契约。
Executive glossary

结合本场景看懂关键术语

DAG（有向无环流程图）
本月报告从冻结数据向对账、指标、签署推进；发现数据问题后以修复请求结束，重述数据用下一次 Run 处理。
AND-join（多路汇合）
交易、支付和总账三份快照都到齐且属于同一 data cut，质量对账步骤才允许启动。
Data cut（冻结数据切片）
某个法人、期间、切片编号下不可悄悄变化的报告输入；重述必须产生新切片和新 Run。
Outcome（业务完成结果）
签署分发和要求数据修复都是完整结果；系统明确记录是哪一种，而不只显示笼统的“流程完成”。
Grounded AI（有依据的生成）
模型只能依据已核验指标和证据生成叙述，不能自行重算监管数字或把质量例外写成正常。

Author burden · minimal

Tool 只交 payload

流程作者声明 output Schema；只有存在业务对齐需求才写 binding_keys。Tool 不计算 hash、不生成 Artifact ID，也不复制 Run 元数据。

Runtime · automatic

finalize 一次计算

Runtime 生成版本 artifact_id、流式计算内容 sha256/size；声明输入与冻结 Tool/Profile 的摘要只存 producer Attempt 一次。

Out of scope · lightweight

临时文件明确排除

Working / logs / Prompt / .staging / SessionOutput projection 不承担业务 binding 或派生摘要，也不能被当作可复用正式产物。

为什么不在 Artifact 重复输入 hash？一个 Attempt 可能发布多个 Artifact。每条记录只保留 producer attempt_id，页面从 Attempt/Fanout Item 解析唯一的 input_snapshot_hash；便携导出需要时才内联。

输入到输出的约束链

  1. session 输入原始文件不可原地覆盖；修订产生新 path/hash。
  2. Run 输入0_SessionContext/InputManifest.json 冻结本次声明输入。
  3. Step 输入Manifest/locator 解析；Adapter staging 只是 Attempt 临时副本。
  4. 中间过程Working 可清，不承担业务 binding/派生摘要，不能被下游当正式产物。
  5. 正式输出先写 .staging；finalize 自动生成版本 ID/hash，再原子发布到既有 Output。
  6. 对外目录SessionOutput 只做可重建投影；canonical Manifest 保持唯一。
为什么 task 没有目录？

OpenCrew 的 session 与 task 1:1 配对。task 从数据库引用 session、Run 与 Artifact ID；再复制一棵 task 文件树只会制造双份字节和清理竞态。
