Why FlowSpec here

海量材料处理的难点是身份、证据与范围

尽调材料会持续补充，单个文件可并行处理，但结论必须限定在同一 matter 和 scope revision 内；法律与财务判断既要共享证据索引，又必须保持独立复核，最终由专业人员承担结论责任。

01

材料不齐时先补件而非空跑模型

规范支持

Inventory Step 先冻结文档清单；缺失材料以 supplement_requested outcome 结束，补件后在同一业务实例创建新 Run 并更新 input revision hash。

规范约束

旧 Run 的 Artifact 不因文件仍在就自动复用；scope 或清单变化会使旧产物 stale，禁止在原 DAG 内循环等待未知材料。

02

按文档稳定身份进行大规模 fanout

规范支持

fanout 使用 document_id 作为 item_key，声明并发上限、失败阈值和确定性 reduce 顺序；每个子项各自产生 Extract Artifact、UsageRecord 和 item 状态。

规范约束

子项 key 必须唯一，输出模板和 Artifact binding 必须携带该 key；不能按数组位置归并，也不能把失败项静默丢掉后宣称父 Step 完成。

03

Agent 研究与专业结论分层

规范支持

法律 Agent 与财务模型在同一 EvidenceIndex 上并行工作，finding 保留页码/段落引用，再由 Human Task 审阅并发布报告。

规范约束

Agent 工具和网络默认 deny/allowlist，不能直接改权威状态；无 evidence 的 finding 不得 finalize，专业审批必须记录 actor、reason 与 revision。

FlowSpec 在本场景中的作用

FlowSpec 把规模化抽取变成按稳定业务键可追踪、可计费、可局部定位的集合执行，同时用 scope、evidence 和人工责任约束 Agent，避免“处理了很多文件”被误当成“得出了可信结论”。

决策层建议 先看本导读、流程图和 outcome，理解业务控制与可追责结果。开发团队建议 再下钻运行记录、Artifact、AI/成本治理和规范透视，核对实现契约。
Executive glossary

结合本场景看懂关键术语

Fanout（拆分并行处理）
把数据室清单按 document_id 拆成许多独立抽取任务；某份文件的状态、用量和错误不会与其他文件混在一起。
Fan-in（按规则汇合）
所有文档抽取按稳定 key 收拢成 EvidenceIndex，再供法律与财务复核；不是简单把输出按完成先后拼起来。
Item key（子项稳定身份）
document_id 是文档在重试、并行和汇总中的永久名字；数组第几个不是身份，因为清单补件后顺序会变。
Evidence binding（证据绑定）
每个 finding 要能追到具体文档、页码或段落、matter 和 scope revision，避免跨项目或跨版本引用。
Run（一次范围版本）
材料不齐的 Run 以补件请求结束；文件补齐后用同一 matter 的新 Run 重做，旧结论不会悄悄混入。

Author burden · minimal

Tool 只交 payload

流程作者声明 output Schema；只有存在业务对齐需求才写 binding_keys。Tool 不计算 hash、不生成 Artifact ID，也不复制 Run 元数据。

Runtime · automatic

finalize 一次计算

Runtime 生成版本 artifact_id、流式计算内容 sha256/size；声明输入与冻结 Tool/Profile 的摘要只存 producer Attempt 一次。

Out of scope · lightweight

临时文件明确排除

Working / logs / Prompt / .staging / SessionOutput projection 不承担业务 binding 或派生摘要，也不能被当作可复用正式产物。

为什么不在 Artifact 重复输入 hash？一个 Attempt 可能发布多个 Artifact。每条记录只保留 producer attempt_id，页面从 Attempt/Fanout Item 解析唯一的 input_snapshot_hash；便携导出需要时才内联。
为什么四个 Demo 的 binding 都非空？贷款、监管报告、尽调和视频产物都需要跨 Run 按 application / entity / matter / project 对齐；这是场景需要，不是全局强制。无 join、re-bind 或跨 Run 对齐的一次性正式产物可省略 binding_keys。

输入到输出的约束链

  1. session 输入原始文件不可原地覆盖；修订产生新 path/hash。
  2. Run 输入0_SessionContext/InputManifest.json 冻结本次声明输入。
  3. Step 输入Manifest/locator 解析；Adapter staging 只是 Attempt 临时副本。
  4. 中间过程Working 可清，不承担业务 binding/派生摘要，不能被下游当正式产物。
  5. 正式输出先写 .staging；finalize 自动生成版本 ID/hash，再原子发布到既有 Output。
  6. 对外目录SessionOutput 只做可重建投影；canonical Manifest 保持唯一。
为什么 task 没有目录？

OpenCrew 的 session 与 task 1:1 配对。task 从数据库引用 session、Run 与 Artifact ID；再复制一棵 task 文件树只会制造双份字节和清理竞态。
