FlowSpec v0.4 · vendor-neutral · AI/Agent-first

把不确定的 AI 执行，收敛为可治理的业务结果

FlowSpec 是一套从 OpenCrew 生产实践中抽取、并用成熟编排体系校准的业务流程规范。它让流程、产物、人责、外部副作用、模型权限与逐笔成本使用同一套身份和工程契约。

Executive brief 决策层

它解决的不是“怎么画图”，而是怎么对结果负责

AI-heavy 业务的问题不是步骤能不能串起来，而是高成本、不完全可靠的外部执行，能否被收敛成可追责、可恢复、可核算的业务事实。

01 · COMMON LANGUAGE

统一团队心智模型

产品、合规、AI、平台和业务开发使用同一套 Process、Run、Artifact、Human Task、Usage 与 Outcome 语言，减少每个项目重新发明编排语义。

02 · CONTROL

让自动化可授权

模型只能在冻结的 Profile、数据边界、工具权限和预算内执行；人工决定绑定输入版本、角色、理由与 revision，AI 输出不会自动成为权威事实。

03 · ACCOUNTABILITY

让结果可解释

每个业务结果都能回答：基于哪版输入、经过哪些步骤、产物来自哪里、谁批准、外部操作是否发生、模型调用花了多少钱。

04 · REUSE

把经验变成平台资产

从 OpenCrew 生产防御代码中提炼通用不变量，再用贷款、银行报告、尽调和视频四个领域校验，避免规范只对来源业务成立。

必须诚实表达的边界

当前可执行 Demo 证明的是目标契约自洽、拓扑闭合、确定性重建与 UI 投影一致；它不证明分布式 claim / lease / fencing、真实并发、进程崩溃恢复或 reconcile worker 已完成。FlowSpec 是统一规范与目标契约，不是已经生产化的通用工作流引擎。

Where it came from

从生产教训出发，不从空白 DSL 出发

规范先把现有实现中的可靠经验显式化，再去业务化，并用不同体系与不同专业场景反复施压。

Production

OpenCrew 工具会话

强类型 Variables、白名单 patch、Workspace、OutputManifest、心跳恢复、事件与本地 Usage 计量已经在真实业务中工作。

Calibration

成熟体系校准

用 Control-M、Airflow、Temporal、Step Functions、Argo 与 BPMN 对照术语、资源、恢复、人工卡点和 artifact 取向。

Abstraction

显式化与去业务化

把视频领域的 session、task、attempt、slot 与外部模型调用重新厘清，形成稳定身份和分层契约。

Validation

四个专业场景反证

用监管审批、多源报告、海量文档和多模态制作检验并行、汇合、人审、昂贵调用和返工是否仍能统一表达。

Core model 开发团队必读

业务生命周期可以循环，每次执行仍保持可验证

核心选择是：稳定的 session + task 表达业务实例；一次 Run 表达静态 DAG；补件、重审和返工创建新 Run，以修订链形成完整业务循环。

DAG · 有向无环流程图
一次 Run 只向前执行，所以依赖可静态检查。业务退回不在图里倒着跳，而是创建下一次 Run。
Artifact · canonical 可消费产物
Runtime 在 finalize 自动生成版本 ID/内容 hash，并关联 producer Attempt 的单份输入摘要；只有确需 join/re-bind 时才声明业务 binding。临时文件不适用。
Outcome · 业务完成结果
批准、拒绝、补件、返修和正式交付都可以是完整结果，不用把所有正常分支挤成一个“成功”。
Reconcilable · 先对账再补做
放款、分发或模型生成响应丢失时，先按稳定 operation key 查询是否已发生，禁止盲目重发。

Graph + user intent 双受众

流程可以分叉汇合，临时运行也必须沿依赖图裁剪

04 · isolatedonly_step

重新单独运行某步骤

默认是 diagnostic，不改正式 Manifest/outcome。若要采用新结果，必须走 from_step 并使受影响下游失效。

diagnostic 计费标记已有发布隔离待补

OpenCrew Analysis_V1 已有 full/range/from/only/rerun 的领域入口与依赖缺失检查；但它按硬编码线性步骤表编译，边界前步骤目前按位置标 reused，plan_hash_match 只供观察。FlowSpec 要求按 DAG 闭包裁剪、按 hash/schema/binding 门控复用，并把 diagnostic 与 canonical 发布隔离。详见 06 · E6、07 · 3.9 与 09 · L4.6。

Design positions

一套能指导实现的规范，必须在真实分歧上选边

FlowSpec 不追求把所有引擎特性并成最大集合；它为 AI/Agent 密集型、artifact 密集型和高成本副作用场景选择一组可执行的最小内核。

P1
选择每个 Run 是声明式 DAG
不选择运行时执行任意回边 / 通用循环 DSL
保留静态校验与恢复推导；真实业务循环通过跨 Run 修订链表达。
P2
选择物化状态 + append-only 审计事件
不选择强制事件溯源与确定性重放
恢复需要高效快照，审计需要不可变时间线；transactional outbox 仍明确标为 proposed。
P3
选择按副作用类别定义恢复
不选择一个 retry_count 解决所有失败
pure / idempotent / reconcilable / non_idempotent 分别决定重算、去重、对账或 fail-fast。
P4
选择canonical Artifact 是一等事实
不选择裸路径即结果，或所有文件都背元数据
Runtime 自动算版本 ID、内容 hash 与 producer 输入摘要；binding 按需声明。Working、日志、Prompt、staging、投影排除，保住收益而不制造普遍负担。
P6
选择Human Task 是持久 work item
不选择用布尔按钮或 blocked 冒充审批
先 dispatch 再 waiting；决定绑定 actor、role、reason、input hash 和 expected revision。
AI
选择Agent 循环留在有界 Tool 内
不选择把每次思考画成 Process 回边
编排器看到 Step 的最终 Artifact；每轮 Model Invocation 仍单独计量、计费并以 Agent Execution 归组。

Logs + physical workspace 双受众

每个事实有明确权威，每个文件有可解析位置

FlowSpec 不把“日志”当成一个万能文本桶，也不为 session、task、Run、Step 各复制一棵文件树。业务审计、费用、诊断、Prompt、Artifact 与服务日志分平面治理。

数据库、文件与平台日志各司其职

UI 可以把它们组合成一条时间线，但实现和审计必须知道哪一份才是权威。

DatabaseRun/Step 状态快照、session_events 审计事件、Usage/Cost ledger；不存高容量 stdout/stderr。
Workspace冻结输入、Manifest、Artifact、Prompt 与按 Step Attempt 隔离的诊断文件；大文件可换成带版本 URI。
Platform sinkAPI、worker、scheduler、数据库进程日志位于 session Workspace 外，由部署配置轮转与告警。
ProjectionUI tail、events.ndjson 证据包和 SessionOutput 都可重建，不成为第二权威源。

AI 与费用如何被管住

一次 AI 调用：先检查权限，再执行，最后逐笔记账

例如生成一段视频：系统必须先确认可用哪个模型、数据能否外发、Agent 能做什么以及预算是否足够；调用结束后，再记录实际模型、用量、费用和对账线索。

第 1 步 · 调用前规则

这次调用允许发生吗？

AI Execution Profile 是随 Run 固定的规则卡。业务代码不能临时绕过它。

模型限制只允许批准的供应商、模型版本和运行区域数据限制哪些数据可外发、可保留或可用于训练Agent 权限允许读取哪些文件、调用哪些工具和网络额度限制最多轮数、token、媒体时长和费用输出要求必须满足结构、引用、内容安全和业务校验失败处理是否允许备用模型；禁止无提示地换模型
第 2 步
费用闸门预留 → 执行 → 结算

预计花 10 元，先占用 10 元额度；实际花 8 元，就记 8 元并释放剩余 2 元。额度不足时不发起调用。

第 3 步 · 调用后事实

实际调用了什么、花了多少？

每次真正发给模型供应商的调用都产生一条 UsageRecord；Agent 多轮执行也要逐次记录。

调用身份属于哪个 Run、Step、Attempt 和业务操作实际模型最终使用的供应商、模型版本和请求编号实际用量输入/输出 token，或图片、音频、视频单位费用可信度未知、估算、暂定或账单最终值对账线索价格版本、供应商请求和稳定操作键后续纠错原记录不覆盖；用新的更正记录保留前后链条
模型先产出候选内容

结构、引用、媒体和业务规则检查通过后，才能成为正式业务产物。

Agent 只能在授权范围内行动

只能读取获准输入、使用白名单工具和网络，不能直接修改权威状态或发布结果。

人工决定同样需要留痕

必须记录谁、以什么角色、基于哪版输入、为什么批准或退回。

从今天到生产级平台

三列表示同一能力的三个建设阶段

从左到右分别回答：今天可直接复用什么；采用 FlowSpec 后必须统一什么；多机器、大并发和昂贵外部调用上线前还要补什么。

1 · 今天已有的基础

可直接复用

OpenCrew 已能运行工具会话、保存工作目录和事件，支持部分暂停、恢复和范围重跑，也能记录部分模型用量与估算费用。

现在可以依赖
  • 文件交接：每次会话有 Workspace，步骤通过 Manifest 和 Output 交接。
  • 运行追踪：已有持久事件、部分 Attempt 日志和依赖缺失检查。
  • 用量基础：local_usage_log 可记单位、估算费用、币种和价格版本。
还不能据此声称所有业务都已使用统一 Process/Run/Artifact 契约，也不能声称所有模型调用都有实际账单费用。
团队怎么做保留并复用现有数据库和目录骨架，不大规模迁移 OpenCrew。

2 · FlowSpec 统一的工作方式

团队统一目标

让不同业务用同一组身份、状态和工程契约描述流程，从而能共用运行时、审计、UI 和成本治理。

采用后必须能回答
  • 这次 Run 使用了哪版流程、工具、模型规则和输入？
  • 每个步骤依赖什么、产生什么，返工为何创建新 Run？
  • 谁批准了什么；每次模型调用用了多少、花了多少？
  • 某条分支为何关闭，某个正式产物由哪次 Attempt 产生？
当前边界四个 Demo 已证明这些契约可以闭合和重建，但 OpenCrew 通用运行器尚未完整实现它们。
团队怎么做后续新能力按这套字段、状态、目录和 API 对齐，避免各业务继续发明自己的协议。

3 · 规模化上线前的可靠性能力

上线前补齐

当多个 worker 同时运行、外部调用昂贵且可能超时时，还需要自动协调、对账和崩溃恢复。

生产环境还要保证
  • 不重复执行：同一任务只能被一个有效 worker 领取，旧 worker 不能继续写结果。
  • 结果不明先对账：放款或视频生成超时后，先查询是否已经成功，再决定是否补做。
  • 崩溃可恢复：从安全检查点继续，不必整条昂贵流程重来。
  • 并发受控：公平分配模型额度、速率和共享资源。
未完成前的运行边界只能采用单 worker、受限流量或人工对账，不能把 Demo 跑通理解成分布式问题已经解决。
团队怎么做按场景风险把这些能力设为上线 Gate；高成本或不可重复副作用的场景必须提前建设。
开发精度说明：数据库有字段，不代表系统已经稳定写入该事实。例如 actual_cost_micros 虽然存在，但本地默认路径通常不写；数据库保存的是 pricebook_version，价格表本身仍在代码配置中；客户价和内部结算价目前由报表按倍率计算，并没有逐笔结算状态。

Calibrated, not copied

借成熟体系的强项，但不绑定任何一家引擎

Build order 依赖顺序，不是价值排名

先建立稳定事实，再叠加规模与运营能力

Artifact、Human Task、Usage 与 fanout 都需要先挂在稳定的 Run / Step / Attempt 身份上。不能因 AI 成本紧迫，就先造一套脱离执行事实的旁路账本。

P0-A

定义编译 + Run 基座

Process/Registry 校验与 digest；Run/Step/Attempt；原子 claim；分支闭包与 outcome。

退出条件：每次执行都有冻结定义与闭合状态。
P0-B

Typed Context + Artifact + Storage

Schema、白名单 patch、显式 path base、Attempt 私有写、诊断 locator；仅 canonical Artifact 自动生成 hash/provenance/validity，binding 按需，finalize 原子发布。

退出条件：能证明正式产物属于谁、物理在哪、由何产生；Tool 与临时文件无需重复造元数据。
P0-C

Human Task / Callback

持久 work item、waiting、actor/role/reason、input hash、expected revision 与幂等回调。

退出条件：责任移交与并发决定可审计。
P1-A

AI Profile + Usage + Budget

Profile enforcement、统一 Invocation、typed measurement/cost、reserve/settle/release。

退出条件：所有模型路径可授权、可逐笔核算。
P1-B

Typed fanout / fan-in

stable item key、逐项状态/产物/用量、并发与失败阈值、确定性 reduce。

退出条件：大规模集合执行可定位、可局部恢复。
P2

对账、资源与运营面

reconcile worker、operation receipt、lease/fencing、snapshot cursor、SLA overlay。

退出条件：歧义结果、崩溃和规模化资源竞争可收敛。
上线 Gate 不按编号机械后置

P2 是通用平台化顺序，不是安全能力的延期许可。首批场景若已使用多 worker、长时昂贵任务或不可盲重发的外部副作用，相应 lease/fencing、reconcile 与 checkpoint/心跳恢复必须前移为该场景的上线条件；否则只能维持单 worker、受限流量或人工对账的明确边界。

What to align on

团队统一规范之前，需要明确同意什么

FlowSpec 的价值来自核心纪律一致，而不是字段越多越完整。下面两组问题分别对应管理决策和工程接入。

决策层需要确认

  • 接受“业务实例稳定、业务返工创建新 Run”的审计模型。
  • 把 Artifact、人责、AI 权限和逐笔成本视为产品能力，而不是日志附件。
  • 接受审计事件、费用事实、诊断文件和服务日志分层治理，避免“一份日志包打天下”。
  • 重大上线决策以实际验收证据为准，不能用 Demo 跑通代替生产可靠性证明。

开发团队需要遵守

  • 新流程以 executable Process、Registry、Schema 和冻结 digest 为契约入口。
  • task 不复制 session 文件树；Step 输入走 Manifest/locator，正式输出只从 canonical OutputManifest 发布。
  • 诊断日志带 Run/Step Attempt 身份、级别/channel、可见性与保留策略；不得从文本日志反推状态或费用。
  • 每个 Model Invocation 单独记录 Usage/Cost；Agent 内循环不能绕过 Profile 与预算。
