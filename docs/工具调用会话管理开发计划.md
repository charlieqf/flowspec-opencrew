## 1. 目标

本计划把 Tool Use Session PRD 落成可执行工程任务，目标不是一次性重写全部 Tool Library，而是先建立可验证的执行合同，再通过 adapter 和首批工具迁移验证闭环。

完成后应达到：

1. 每次 Run / Rerun 都有独立 Tool Use Session 运行根目录。
2. Plan Runner 可以创建 Tool Use Session、执行 S0、运行工具、写回 DB 状态。
3. 工具不直接访问 DB、OpenCode 管理 API、provider key 或 workspace 外路径。
4. LLM / VLM / ASR 调用通过本机 broker / resolver 完成，Phase 0 写 `local_usage_log`。
5. 工具输入、输出、Prompt、模型调用审计和页面绑定都有机器可读 manifest。
6. Attempt result index、`session_files`、`session_events` 与 workspace artifacts 对齐。
7. 现有 `ToolLibrary/Analysis/tool_registry.json` 可以归一化为 Plan Runner 可执行的 normalized registry。

## 2. 非目标

本计划不做：

1. 一次性迁移全部 21 个 Analysis 工具。
2. Phase 1+ Managed Gateway。
3. 完整计费、余额、价格本或网关 `usage_ledger`。
4. 前端大改版。
5. 删除旧 runner。
6. 生产级 GC 后台任务；本阶段只定义 GC 元数据和手动清理入口。
7. 在 M1-M3 阶段修改 `ToolLibrary/Analysis/` 具体业务脚本。

## 3. 总体顺序

实施顺序必须先合同、再验证器、再 Runner，最后迁移工具：

```text
Schema / contracts
  -> registry normalize + validation
  -> Tool Use Session root + S0
  -> broker / resolver MVP
  -> Plan Runner MVP
  -> 首批工具迁移
  -> result index / page binding
  -> 分批扩展和 GC
```

阶段边界：

1. M1-M3 只建设基础设施、schema、registry normalizer、Tool Use Session root、S0、broker/resolver fake path、Runner noop 和 adapter，不改 `ToolLibrary/Analysis/` 具体业务脚本。
2. M4 开始才进入真实业务脚本迁移。
3. `ToolLibrary/Analysis/` 业务脚本迁移由专门负责人执行；平台侧提供合同、受控 IO helper、broker/resolver、Runner 和测试夹具。
4. 在业务脚本完成迁移前，旧 runner 和 adapter fallback 必须保留。

## 5. 阶段 1：合同 Schema 与验证器

### 5.1 新增 Schema

建议新增目录：

```text
backend/opcrew_backend/tool_sessions/schemas/
```

定义以下 JSON schema 或 Pydantic model：

本阶段新增的所有机器可读 schema 必须统一使用字符串 `schema_version`，例如 `"1.0"`。

1. `Variables.json` schema，`schema_version: "1.0"`。
2. `InputManifest.json` schema。
3. `State.json` schema。
4. `OutputManifest.json` schema。
5. `PromptManifest.json` schema。
6. `DependencyCheckResult.json` / blocked report schema。
7. `ModelCall*_request/response` audit schema。
8. `ToolResult` stdout / file result schema。
9. `SessionRunSummary.json` schema。
10. `SessionOutput/manifests/result_index.json` 最小 schema。
11. `SessionContextPatch` schema。
12. `ResyncResult.json` schema。

`DependencyCheckResult` 必须覆盖 PRD §12 的 blocked 输出：`status=blocked`、`missing_dependencies[]`、`kind`、`required_from`、`required_path`、`suggested_action`。

`ModelCall` audit schema 必须覆盖 PRD §17.4 的字段集：`tool_use_session_id`、`step_index`、`tool_name`、`task_id`、`opencrew_session_id`、`opencode_session_id`、`attempt_id`、model provider、model id、system prompt path、user prompt path、input files、output summary、error summary、`request_id` / `local_usage_id` / `gateway_request_id`、`provider_mode`、`billing_mode`、usage summary、`sensitivity` 和 redaction 状态。

### 5.2 Registry Normalizer

新增 normalized registry 生成器：

```text
backend/opcrew_backend/tool_sessions/registry_normalizer.py
```

职责：

1. 读取现有 `ToolLibrary/Analysis/tool_registry.json`。
2. 保留 `id/name/script/stage/cost_level/uses_llm/uses_vlm/supports_resume` 等字段。
3. 将规范 token 自动映射到：
   - `reads_session_context`
   - `consumes_outputs`
   - `runtime_dependencies`
   - `environment_hints`
   - `provider_config_dependencies`
   - `optional_dependencies`
4. hard dependency 保留在 `reads_session_context` / `consumes_outputs` / `runtime_dependencies` / `environment_hints` / `provider_config_dependencies` / `manual_dependencies`；soft dependency 必须进入 `optional_dependencies`，Runner 后续按 warning / degraded path 处理，不能把 soft 误判为 blocked。
5. `provider_config_dependencies` 用于标记 PRD §16.1.1 中不能交给沙盒工具直读的 DB / provider config，后续由 broker / resolver 注入。
6. `environment_hints` 用于标记 `gpu_or_mps_for_speed` 这类环境优化提示，Runner 不应按 `shutil.which()` 判断为缺失并 blocked。
7. 对自由文本 token 输出 `manual_dependencies`。
8. 如果 normalized registry 仍有 unresolved token，则 validation fail。
9. 输出 normalized registry artifact，供 Plan Runner 使用。

自由文本 token 首批必须人工归一化：

```text
13 detail scheme
14 detail segment descriptions
target balanced_or_summary
task_opencode_session_or_fallback
human_scene_transition_overrides
user_recomposition_instruction
```

### 5.3 验收

1. normalized registry 生成成功。
2. 对未归一化 token，校验器能给出 tool id、原 token、建议 kind、待补字段。
3. Plan Runner 不读取原始 registry 的自然语言字段做执行判断。
4. schema 测试覆盖合法样例和失败样例。
5. 本阶段不修改 `ToolLibrary/Analysis/` 业务脚本。

## 7. 阶段 3：本机模型 Broker / Resolver MVP

### 7.1 背景

`03/06/14/17/02_audio_asr` 等工具需要 LLM / VLM / ASR 调用，但工具不能持有 key。Phase 0 必须走本机 broker / resolver，由其读取盒子本地密钥库并写 `local_usage_log`。

### 7.2 实现任务

MVP 必须基于既有 `backend/opcrew_backend/services/provider_resolver.py`、`local_secrets.py`、`local_usage.py` 扩展。新增 `model_broker.py` 只作为工具侧受控入口包装层，避免形成第二套 provider / secret / usage 逻辑。

新增：

```text
backend/opcrew_backend/tool_sessions/model_broker.py
```

或复用已有 provider resolver，暴露受控入口：

1. `submit_model_call(request)`。
2. 输入只允许 `provider_mode`、`billing_mode`、`model_id`、`modality`、`request_id`、payload、proxy_policy。
3. broker 根据 `key_ref` 从盒子本地密钥库解包真实 key。
4. broker 注入 auth，调用 provider 或 OpenCode provider 代理。
5. broker 写 `local_usage_log`。
6. broker 返回 response 和 sanitized audit summary。
7. broker 不把 key、auth header、cookie 写入工具文件或 stdout。
8. broker 接收 Runner 下发的 step-level idempotency key，并写入 ModelCall audit。
9. broker 不自行生成新的业务 idempotency key；如果缺失必须拒绝调用并返回 blocked / invalid_request。
10. broker 使用 `request_id` + idempotency key 与 `local_usage_log` 对账，避免 retry / resume 重复记账。
11. broker 将 ModelCall audit 持久化到 `Prompt/` 或 Runner 指定的审计路径。

### 7.3 最小范围

MVP 只需要支持首批迁移工具需要的调用类型：

1. `06` 需要 VLM / image model。
2. `14` 可能需要 LLM / VLM。
3. `02_audio_asr` 需要 ASR provider。

首批可先选一个模型工具，避免一次覆盖全部 modality。

### 7.4 验收

1. 工具进程不读取 provider key。
2. broker 可完成一次 fake model 调用和一次真实可选调用。
3. `local_usage_log` 有记录。
4. ModelCall audit 文件包含 `request_id`、Runner 下发的 idempotency key、`local_usage_id`，不含 secret。
5. 相同 idempotency key 的 retry 不重复写入成功用量。
6. broker 在缺少 idempotency key 时拒绝调用。
7. Debug event 已脱敏。
8. 本阶段不修改 `ToolLibrary/Analysis/` 业务脚本；模型调用可用 fake provider 或 adapter 测试。

## 8. 阶段 4：Plan Runner MVP

### 8.1 实现任务

新增或扩展 WorkflowAssistant runner：

```text
backend/opcrew_backend/tool_sessions/runner.py
```

职责：

1. 读取 latest confirmed plan。
2. 创建 Attempt。
3. 创建 Tool Use Session。
4. 运行 S0。
5. 读取 normalized registry。
6. 按 step 执行 tool。
7. 注入 `--tool-session-root`。
8. 注入 `--step-id` / `--tool-id`。
9. 注入 `--print-json`。
10. 注入 `--resume` / `--force-rerun`。
11. 读取 tool result JSON。
12. 校验 `SessionContextPatch` ownership，并只合并 normalized registry 中声明允许写入的字段。
13. 写 DB step 状态和 `session_events`。
14. 汇总 `SessionReport/SessionRunSummary.json`。
15. 生成或刷新 `SessionOutput/manifests/result_index.json`。
16. 更新 attempt result index。
17. 生成和管理 step-level idempotency key，并下发给工具和 broker。
18. `--force-rerun` 时执行 `retry_count++`，并 bump idempotency key。
19. 监控 step `heartbeat_at`，超过 step-level 阈值时标记为 `stale_running` 或按策略转 `failed`。
20. DB 写回失败时将 attempt 标记为 `completed_with_sync_error` 或等价可恢复状态。
21. 提供 resync API 或内部命令，从 `SessionOutput` / `SessionReport` 重建 attempt result index、`session_files` 和缺失的 sync event。

Heartbeat 阈值默认策略：

1. 现有 `ToolLibrary/Analysis/tool_registry.json` 的 `estimated_runtime` 形态是 `{ "basis": "...", "relative": "very_low|low|medium|high|very_high" }`，不能直接当秒数使用。
2. normalized registry 应把 `estimated_runtime.relative` 映射为 `estimated_runtime_seconds`，默认映射建议为：`very_low=60`、`low=180`、`medium=600`、`high=1800`、`very_high=3600`。
3. 默认 heartbeat 阈值为 `max(estimated_runtime_seconds * 3, 300)`。
4. 如果 registry 缺少 `estimated_runtime.relative` 且 normalized registry 也缺少 `estimated_runtime_seconds`，默认阈值为 900 秒。
5. RunnerStep 必须持久化 `heartbeat_timeout_seconds`，并优先使用 normalized registry 中对应工具的 `heartbeat_timeout_seconds`。
6. normalized registry 可以通过 `heartbeat_timeout_seconds` 覆盖。
7. 高成本 VLM / 长视频工具应显式配置 `heartbeat_timeout_seconds`，避免误判。

### 8.2 持久化策略

MVP 可先使用 `workflow_plans.plan_json.execution_state`，但 schema 必须稳定：

```json
{
  "schema_version": "1.0",
  "tool_use_session_id": "",
  "attempt_id": null,
  "steps": []
}
```

后续迁移到：

```text
workflow_plan_runs
workflow_plan_steps
```

### 8.3 验收

1. Runner 能执行 S0 + 一个 noop tool。
2. 刷新后能从 DB 恢复执行状态。
3. step failed / blocked / completed / stale_running 能进入 Debug Console。
4. `Variables.json` patch 合并有 ownership 校验，未声明字段会被拒绝。
5. 高成本 step 默认需要 confirmation。
6. 强制 rerun 会 bump retry count 和 Runner 管理的 idempotency key。
7. DB 写回失败会进入 `completed_with_sync_error`，resync 后可恢复到 completed 或明确 failed。
8. heartbeat timeout 使用默认策略，registry override 生效。
9. 本阶段只执行 noop / adapter，不修改 `ToolLibrary/Analysis/` 业务脚本。

## 11. 阶段 7：扩展迁移和 GC

### 11.1 扩展迁移

首批验证通过后按批次迁移：

1. foundation 工具：`01/02/04/05`。
2. semantic 核心：`03/08/10/11/12`。
3. 高成本视觉工具：`06/14`。
4. scheme / export / QA：`13/13_01/15/16/17`。
5. 其它子工具：`02_0/05_1/05_2/07/09`。

每批迁移必须保留旧 runner fallback。

### 11.2 GC MVP

先做手动 cleanup 命令或内部 API：

1. 列出 Tool Use Session。
2. 标记 `archived` / `gc_candidate`。
3. 跳过 latest attempt。
4. 跳过被 result index / `session_files` 引用的文件。
5. 清理历史 `Working/` 缓存。
6. 严格执行 DB-first：先写归档 / GC 事件，并更新将被删除文件的索引状态，再删除 workspace 文件。
7. 文件删除失败时写 cleanup event，不回滚已完成的 DB 标记。

生产级后台 GC 仍是非目标，但本阶段应预留 retention config 字段或配置项：

1. `keep_latest_attempt=true`。
2. `keep_recent_attempts=N`。
3. `working_cache_ttl_days`。
4. `keep_downloadable_session_output=true`。
5. `dry_run=true/false`。

### 11.3 验收

1. 不删除 latest attempt 可下载交付物。
2. 不删除 DB 仍引用的 result index 文件。
3. GC 事件和文件索引状态更新发生在文件删除之前。
4. cleanup 失败可诊断。

## 13. 风险和缓解

| 风险 | 缓解 |
| --- | --- |
| 迁移范围过大 | 先迁移 `01` + 一个模型工具，旧 runner 保留。 |
| 平台基础设施开发干扰业务脚本维护 | M1-M3 不修改 `ToolLibrary/Analysis/`，M4 起由业务脚本负责人按合同迁移。 |
| registry 自由文本 token 无法自动推导 | validation fail + 人工归一化，不让 Runner 猜。 |
| 模型 broker 泄露 key | broker 只返回 sanitized audit，测试覆盖 secret redaction。 |
| 高成本 step resume 重复调用 | idempotency key + ModelCall audit + 默认不重复调用。 |
| 页面绑定回归 | latest attempt result index 优先，legacy fallback 写 warning。 |
| Tool Use Session 目录膨胀 | GC 元数据先落地，手动 cleanup 后再做后台任务。 |
| DB 写回失败但文件已生成 | 标记 `completed_with_sync_error`，提供 resync。 |
| heartbeat 阈值过短导致长任务误判 stale | 使用默认阈值策略，并允许 registry 按工具覆盖。 |
| resync 被滥用导致 attempt 状态漂移 | resync 只允许从当前 Tool Use Session manifest 重建索引，执行前后写 debug event，并保留原状态审计。 |

边界：不修改 `ToolLibrary/Analysis/` 业务脚本。

### M3：Runner + Noop Tool

交付：

1. Plan Runner MVP。
2. noop tool contract。
3. State / OutputManifest / ToolResult。
4. heartbeat / `stale_running` 回收。
5. idempotency key / retry count 管理。

完成标准：Runner 能执行 noop step、恢复状态，并能处理 heartbeat 超时和 DB 写回失败后的 resync。

边界：只允许 noop / adapter 验证，不修改 `ToolLibrary/Analysis/` 业务脚本。

### M4：首批真实工具

交付：

1. 平台侧 Runner 从 normalized registry 按 `tool_id` 派发 step，替代 M3 的硬编码 noop 路径。
2. 平台侧提供 adapter contract；未注册 adapter 时必须 blocked，不直接调用 `ToolLibrary/Analysis/` 业务脚本。
3. 平台侧实现 hard dependency 缺失 blocked、soft dependency warning / degraded path 的数据基础。
4. broker / resolver MVP 和 local_usage_log 对账保持可用。
5. `01` 迁移和一个模型工具迁移由业务脚本负责人执行，平台侧只提供 adapter、helper 和验收测试。
6. broker 在本计划当前实现中仍是 fake / audit-only；业务侧接入 `06` 之前，平台必须补真实 OpenCode VLM HTTP 调用、从 `local_secrets` 解析 `auth_ref`、写 `local_usage_log` 的完整路径。
7. Subprocess adapter 必须 scrub 子进程环境，只传基础 runtime 变量和受控 `PYTHONPATH=<repo_root>/backend:<repo_root>`；不得把 provider key、auth header、cookie、proxy、DB URL 透传给业务脚本。

完成标准：adapter smoke 可完成；真实 `ToolLibrary/Analysis/` 脚本迁移由业务负责人接入后再跑短视频 smoke。

### M5：页面绑定闭环

交付：

1. result index。
2. session_files sync。
3. 页面读取 latest attempt result index。
4. `SessionOutput/` 标准子目录。
5. result index / `session_files` resync。
6. 如落地 `workflow_plan_runs` 或等价 attempt/run 表，`tool_use_session_id` 必须有 DB 唯一约束。
7. 页面文件列表不得通过扫描 `tool_use_sessions/` 任意内部目录推断结果；必须依赖 result index / `session_files` 同步后的 `SessionOutput` 条目。

完成标准：页面不依赖目录扫描展示最新结果。
