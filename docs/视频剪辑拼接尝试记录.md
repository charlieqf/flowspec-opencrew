# 视频剪辑拼接尝试记录

本文档用于持续记录 OpenCrew 视频剪辑、拼接、合成、边界修补、帧率处理、音视频时长对齐等实际尝试。

用途：

- 记录每次拼接问题的现象、素材、工具链路和判断依据。
- 记录尝试过的方案，包括失败方案、备选方案和最终采用方案。
- 沉淀可复用的处理策略，避免后续遇到类似问题时重复试错。
- 为后续产品化能力提供案例依据，例如自动 retime、边界缓动、帧率保持、GOP 设置、字幕渲染降级等。

追加规则：

- 每次新增记录请按“尝试记录 YYYY-MM-DD 编号”追加到文档末尾。
- 记录应尽量包含：问题现象、输入素材、原始媒体信息、尝试方案、结果、最终结论、遗留观察。
- 不要求每次都有代码改动；只要是有价值的剪辑/拼接实验，都可以记录。
- 如果某次记录来自具体任务，可以在标题或“来源”中写明 Task / Session，但文档本身保持通用。

## 尝试记录 2026-07-06-001：DanceMimic 两段动作拼接边界轻微抖动

### 1. 来源

本次问题来自 DanceMimic_V1 动作模拟任务的一次拼接验收：

- UI 标识：Task #25 / Session #26
- 会话工作区：`/Users/duheng/.opencrew/sessions/26/workspace`
- 最终成片路径：`SessionOutput/storyboard/Working/ShotPlan_Final.mp4`
- 参与拼接的两个片段：
  - `dak_0001_Video_Final.mp4`
  - `dak_0002_Video_Final.mp4`

用户反馈：两个片段拼接时有一点小抖动，主要发生在 `dak_0001` 到 `dak_0002` 的边界。

### 2. 原始状态

原始执行结果中，规划时间线与实际模型输出时长不一致：

| 片段 | 规划时长 | 原始 Final 视频时长 | 差异 |
| --- | ---: | ---: | ---: |
| `dak_0001` | 8.483s | 8.042s | 视频短约 0.441s |
| `dak_0002` | 8.517s | 9.042s | 视频长约 0.525s |

原始合成器输出：

- 合成方式：`ffmpeg_concat_filter_reencode`
- 输入片段帧率：24fps
- Scene/ShotPlan 合成输出：被强制转为 30fps
- 边界时间：按实际片段时长落在约 8.042s，而不是规划时间线的 8.483s

初步判断：抖动不是黑帧，也不是播放器卡顿，而是“边界时长漂移 + 帧率重采样 + 第二段起步动作突变”叠加造成的。

### 3. 排查证据

#### 3.1 边界帧观察

抽取 `7.75s-8.50s` 附近边界帧后，观察到：

- `dak_0001` 最后一帧和 `dak_0002` 第一帧姿态接近。
- `dak_0002` 第 2-5 帧开始快速抬手。
- 当前 24fps 素材被合成器重采样到 30fps 后，边界动作分布变得不均匀，肉眼会感觉轻微抖一下。

#### 3.2 帧差指标

对边界附近连续帧做灰度 MAE 检测，原始 `current30` 版本无异常尖峰，但平均变化较高，说明不是单帧硬跳，而是短窗口内动作节奏不平滑。

#### 3.3 关键链路

本次主要涉及两个工具：

- `OpenCrew/ToolLibrary/Analysis_V1/05_02_VideoPlanExecutor.py`
  - 负责生成或复用单段视频，并进行音视频同步。
- `OpenCrew/ToolLibrary/Analysis_V1/06_01_VideoPlanComposer.py`
  - 负责 Scene / Shot / ShotPlan 层级拼接。

### 4. 尝试方案

#### 4.1 方案 A：保持 24fps 直接重新拼接

输出样片：

`/Users/duheng/.opencrew/sessions/26/workspace/S10_06_01_VideoPlanComposer/Working/continuity_experiments/task25_session26_boundary/task25_24fps_concat.mp4`

策略：

- 不做边界融合。
- 不强制转 30fps。
- 保持源片段 24fps 进行 concat。

结果：

- 消除了 24fps 到 30fps 重采样带来的节奏不均。
- 但第二段开头动作本身仍然偏快，残余抖动仍可能被看见。

结论：有帮助，但不是根因修复。

#### 4.2 方案 B：6+6 帧跨段边界焊接

输出样片：

`/Users/duheng/.opencrew/sessions/26/workspace/S10_06_01_VideoPlanComposer/Working/continuity_experiments/task25_session26_boundary/task25_boundary_weld_original_audio.mp4`

策略：

- 第一段末尾取 6 帧。
- 第二段开头取 6 帧。
- 使用 smoothstep 混合替换边界 12 帧。
- 音频使用 24fps concat 版本原音轨。

结果：

- 指标上更平滑。
- 但画面会出现可见重影，尤其第一段背向姿态会混入第二段侧身姿态。

结论：不适合作为默认生产策略，只适合极端边界修补。

#### 4.3 方案 C：只处理第二段开头 12 帧起步缓动

输出样片：

`/Users/duheng/.opencrew/sessions/26/workspace/S10_06_01_VideoPlanComposer/Working/continuity_experiments/task25_session26_boundary/task25_segment2_start_ease_original_audio.mp4`

策略：

- 保留第一段尾部原样。
- 只把第二段前 12 帧替换为从第 0 帧到第 12 帧的 smoothstep 缓动。
- 不改变总时长。
- 音频使用 24fps concat 版本原音轨。

结果：

- 边界差分指标下降。
- 比跨段焊接自然。
- 但仍有轻微融帧重影。

结论：可作为人工修补备选，不建议默认进入主流程。

#### 4.4 方案 D：修正主流程时长策略和帧率策略

这是最终采纳方案。

核心改动：

1. DanceMimic 片段不再锁定模型输出视频时长。
   - 原逻辑：模型吐出多长视频，就把音频裁/补到多长。
   - 新逻辑：以 `video_generation_plan.json` 里的规划时长为目标，轻微重定时视频，同时让音频贴合规划时长。

2. 重定时输出保持源帧率。
   - 原问题：ffmpeg 默认可能把重定时结果写成 25fps。
   - 新逻辑：读取源视频帧率，重定时后仍保持源帧率。

3. 合成器不再强制所有输入转 30fps。
   - 如果所有输入片段帧率一致，则沿用源帧率。
   - 如果输入片段帧率不一致，才回退到 30fps。

4. 合成输出加入稳定 GOP。
   - 按输出 fps 设置 `-g` 和 `-keyint_min`。
   - 避免后续渲染器 seek 时因为关键帧过稀出现卡顿或冻结。

重跑后的最终视频：

- 强制 30fps 重采样导致动作节奏轻微抖动。

## 尝试记录 2026-07-06-002：Task #24 多段 DanceMimic 拼接的局部时间重映射实验

### 1. 来源

本次问题来自 DanceMimic_V1 动作模拟任务的五段连续舞蹈视频拼接：

- UI 标识：Task #24 / Session #25
- 会话工作区：`/Users/duheng/.opencrew/sessions/25/workspace`
- 原始合成视频：`/Users/duheng/.opencrew/sessions/25/workspace/S10_06_01_VideoPlanComposer/Working/shot_001_scene_001_Scene_Final.mp4`
- 实验目录：`/Users/duheng/.opencrew/sessions/25/workspace/S10_06_01_VideoPlanComposer/Working/continuity_experiments/local_retime_optimized`

用户反馈：整体拼接后画面在多个边界有跳帧、卡顿、抖动。声音经过前置修复后已经没有明显问题，因此后续实验只针对视频轨做局部时间重映射，最后再把干净声音轨拼回去。

### 2. 原始问题判断

本次核心问题不是音频，也不是单纯的容器拼接错误，而是生成视频段在边界附近存在姿态突变。

关键观察：

- 文件级首尾帧衔接是正确的，新图/上一段尾帧确实传入了后续段。
- 但模型生成后，后续段开头的实际视频帧并不严格等于输入首帧。
- 最明显的问题不一定发生在“上一段最后一帧 -> 下一段第一帧”，而是发生在下一段自身开头的前几帧内部。

典型例子是 4->5 边界：

- 边界附近最大跳变落在 `846 -> 847`。
- `846` 仍接近上一段连续姿态。
- `847` 突然跳到另一套姿态/尺度。
- `848` 之后又恢复为相对连续的动作序列。

因此，纯粹移动剪切点或丢几帧，只会把跳变挪到窗口内部，不能真正生成缺失的中间运动。

### 3. 声音处理结论

声音问题先独立处理完成：

- 最终干净音轨：`scheme1G_clean_single_source_audio.m4a`
- 来源：直接取一整条连续的 `Audio_Reference_Mixed.wav`
- 处理方式：统一轻微拉伸到当前视频长度，不做分段音频叠加，不做边界 crossfade。

这个方式比“分段音频交叉淡化”更稳，因为不会在边界处叠加两份主体声音，也就不会产生重音或回声感。

后续所有视频实验都固定使用这条干净音轨。

### 4. 视频实验方案

#### 4.1 方案 1H：纯局部时间重映射，清晰帧采样

输出视频：

`/Users/duheng/.opencrew/sessions/25/workspace/S10_06_01_VideoPlanComposer/Working/continuity_experiments/local_retime_optimized/scheme1H_strong_local_retime_clean_audio_h264.mp4`

策略：

- 只处理跳帧边界附近的视频轨。
- 总帧数保持 1058 帧。
- 总时长保持约 35.27s。
- 音频完全沿用 clean audio。
- 不做帧间融合，不做光流插帧，只做清晰帧重采样。
- 对明显跳点压缩上一段末尾若干帧，并拉伸下一段开头若干帧。

优点：

- 画面干净。
- 不会出现半透明重影。
- 不会产生光流扭曲。
- 是更保守、更安全的剪辑型修补。

缺点：

- 对 `846 -> 847` 这种“下一段内部突然换姿态”的问题改善有限。
- 因为没有生成新的中间运动，跳变可能只是被移动或分摊，而不是被真正消除。

验证信息：

- 编码：H.264 video + AAC audio
- 分辨率：720x1280
- 帧率：30fps
- 帧数：1058
- 时长：35.266667s

#### 4.2 方案 1J：局部时间重映射 + 运动估计辅助

输出视频：

`/Users/duheng/.opencrew/sessions/25/workspace/S10_06_01_VideoPlanComposer/Working/continuity_experiments/local_retime_optimized/scheme1J_flow_assisted_clean_audio_h264.mp4`

策略：

- 仍然只处理视频轨。
- 总帧数保持 1058 帧。
- 总时长保持约 35.27s。
- 音频仍然使用同一条 clean audio。
- 在最明显跳点内部替换少量帧。
- 使用运动估计在两个真实端点之间生成过渡帧。

本次替换的核心窗口：

| 跳点 | 替换范围 | 原最大 MAE | 修复后最大 MAE |
| --- | --- | ---: | ---: |
| 约 7s | `213-217` 内部帧 | 26.85 | 12.04 |
| 约 21s | `634-638` 内部帧 | 15.09 | 4.22 |
| 约 28s | `846-850` 内部帧 | 34.05 | 16.37 |
| 约 28s 第二小跳 | `856-859` 内部帧 | 8.91 | 6.09 |

优点：

- 对肉眼最敏感的“突然跳一下”改善更明显。
- 不只是挪动跳点，而是在两个真实姿态之间补出过渡运动。
- 对 4->5 这种下一段开头内部跳变，比纯清晰帧重采样更有效。

缺点：

- 局部可能出现轻微光流残影或形变。
- 如果端点姿态差异太大，手臂、手掌等细节会有一点拖影。

### 5. 为什么对照版 1J 效果比推荐版 1H 更好

用户实际观看后判断：1J 对照版比 1H 推荐版效果更好。

原因总结：

1. 本次跳帧不是普通剪辑点硬切，而是生成段内部前几帧的姿态突变。
   - 1H 只能重新分配已有真实帧的时间。
   - 1J 能在突变两端之间生成中间运动。

2. 1H 的优先目标是“画面干净”，不是“最大程度抹平跳变”。
   - 它不做融合、不做光流，所以不会有残影。
   - 但遇到 `846 -> 847` 这种大幅姿态变化时，它缺少中间帧，只能把跳变挪到别处。

3. 1J 的轻微残影在本场景中比硬跳更容易被接受。
   - 舞蹈动作本身连续运动较多。
   - 用户对“动作突然跳一下”的敏感度高于对局部手臂拖影的敏感度。
   - 因此，即使 1J 存在轻微光流痕迹，主观观感仍优于 1H。

4. 数值指标也支持 1J。
   - 1J 把 7s、21s、28s 这些关键跳点的局部最大帧差显著压低。
   - 特别是 28s 主跳点从 34.05 降到 16.37，虽然没有完全消失，但肉眼卡顿感会明显下降。

### 6. 当前结论

本次任务中，最终更优选择是：

`scheme1J_flow_assisted_clean_audio_h264.mp4`

结论不是“光流一定更好”，而是：

- 如果边界问题只是轻微节奏不均，优先使用 1H 这种清晰帧局部 retime。
- 如果边界问题来自生成段内部姿态突变，且跳变幅度很大，1H 只能缓解，1J 这种运动估计辅助更有效。
- 对 DanceMimic 多段动作连续视频，实际产品化时应允许两级策略：
  - 默认：清晰帧局部 retime，避免画面伪影。
  - 强修复：对高 MAE 跳点启用运动估计辅助，并保留人工预览确认。

### 7. 遗留观察

1. 4->5 的根因仍然是模型生成结果本身不严格服从首帧约束。
2. 后期剪辑可以缓解跳帧，但无法完全替代重新生成边界附近视频。
3. 如果要从源头解决，后续应考虑：
   - 在生成阶段加强首帧/前 0.5s 约束。
   - 对每段生成后自动检测前 10 帧是否出现异常姿态跳变。
   - 如果异常超过阈值，自动触发该段重生成，而不是只依赖后期修补。
4. H.264 转码是必要交付步骤。之前 `mp4v` 编码在部分预览环境里只播音频不显示画面；最终交付应使用 H.264 + AAC。
